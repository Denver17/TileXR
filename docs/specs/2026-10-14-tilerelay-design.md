# TileXR TileRelay: device-driven AllGather-GEMM

Superseded packaging/compatibility requirements: the approved
[ABI-v1-only design](2026-10-19-tilerelay-v1-only-design.md) archives ABI-v0 and
the Host pipeline at `7ccaa16768ae2b2cb0da71d47e864352721de8b0` on
`baseline/tilerelay-v0-pipeline-20261019` and removes their implementations from
the active tree. Requirements/results below describe the original increment;
see [current integration](../TILELANG_INTEGRATION.md) for supported APIs.

## Approval and purpose

The user approved the design on 2026-10-14 and explicitly requested that it
be persisted as a spec followed by development. This document records that
approved scope; it does not add an architectural approval round.

TileRelay replaces per-communication-tile Host launches with one mixed main
kernel per rank and generation. AIV workers move peer-memory data and publish
readiness; AIC workers execute TileLang-generated GEMM arithmetic over multiple
output tiles. Preserve the existing Host pipeline as the comparison baseline
at commit `a17ef9b`.

## Scope and contracts

- First hardware target: two ranks on blue's 910B, CANN 9.1, C++14.
- FP16 contiguous inputs/output, FP32 accumulation. M is partitioned by rank;
  each rank owns its B column shard. Match the current supported tile multiples.
- One mixed main kernel invocation per generation; workers persist only for
  that generation, not for the process lifetime. Kernel count must not grow
  with the number of communication tiles.
- AIC workers process local-input output tiles first and remote-input tiles
  when ready. Multiple AIC workers may compute independent output tiles.
- First version uses full staging, not a ring buffer. Validate staging/flag
  capacities before launch and preserve storage until stream completion.
- Retain the old API and optional build defaults. Add a separate TileRelay
  contract; no benchmark timing types in public runtime interfaces.
- No UDMA, multi-node, arbitrary rank counts, tail tiles, system package
  changes or implicit fallback to the old implementation.

## Data and synchronization

The communicator owns IPC peer mappings. Each rank stages its input in its
owner allocation; remote IPC mappings are used only for peer access. AIV
workers complete payload writes before publishing generation-tagged ready
flags. Local staging makes copied remote data available to AIC consumers.
Use a new `TileXRCommNextMagic` value every generation, not flag clearing.
The communicator cannot be used by other simultaneous operations.

Validate AIV-to-AIC handoff before adding distributed communication. The
implementation must establish GM visibility, matched signal/wait counts,
workspace/UB ownership and independent progress of producers and consumers.
Do not rely on two independently scheduled resident kernels for progress.
No scalar cached polling assumption is accepted without target evidence.

The computation remains generated by the pinned TileLang Ascend compiler.
Prefer source-import/extern integration, not textual rewrites of generated
code. Production Host libraries load external kernel binaries, register them,
and use the repository's direct runtime launch path; do not embed binary
objects or introduce production triple-chevron wrappers.

## Components and failure behavior

- `src/tilelang` and installed headers own plan validation, new launch/ABI and
  reusable device communication/handoff helpers.
- `src/tilelang` owns the reusable TileLang device generator, with opt-in
  offline compilation under `scripts`. Examples own correctness/profiler
  measurement and comparisons. Artifacts carry source/compiler provenance.
- Tests cover Host contracts, device handoff and end-to-end operation.
- Errors propagate explicitly. Bound launchers and stream synchronization;
  after incomplete device work, terminate before releasing referenced storage.

## Verification and performance acceptance

1. Compile and execute a bounded same-device mixed handoff test.
2. Validate peer-memory staging and changed-generation behavior.
3. Validate integrated GEMM for large/small shapes, repeated varying inputs,
   and a delayed rank; exact gathered inputs and existing GEMM tolerance.
4. Establish one main launch per generation, independent of tile count.
5. Establish device communication/compute overlap with separate diagnostic
   evidence when a fused framework trace cannot resolve internal stages.
6. Compare full serial, frozen Host overlap and TileRelay under identical
   device subset, profiler, dtype, shape, warmup and Host timing boundaries.
   Report rank median/min/max, launch counts, remote bytes, latency, and
   explicitly labeled end-to-end effective bandwidth. Do not compare fused
   total time with isolated AllGather stage bandwidth or invent stage times.

Retain the existing one-time HCCL evidence and its coverage boundary; do not
rerun qualification for an unchanged environment. Compilation/Host tests are
not device proof. Speedup is measured, not guaranteed. If compiler/synchrony
capabilities invalidate the architecture, stop and request a revised decision.

## Target-specific calibration

The pinned Ascend codegen handles only selected copy/atomic `call_extern`
names; an arbitrary imported helper is not emitted by that branch. Source
import must therefore not be mistaken for a working generic call interface.
The initial prerequisite uses existing DSL copy and cross-core intrinsics.
No third-party compiler changes have been made.

CANN 9.1 documents mode 2 as synchronization between an AIC and the AIVs
within its group. On A2 this is not the independent AIV0/AIV1 mode 4 available
on 950. Both AIV arrivals must be accounted for; hardware flag counters have
a bounded range. The first probe explicitly pairs each wave with an ACK.
Confirm these signatures and execution behavior with blue's installed SDK;
online documentation alone does not establish the installed implementation.
See [CANN 9.1 CrossCoreWaitFlag](https://www.hiascend.com/document/detail/en/CANNCommunityEdition/910/API/ascendcopapi/docs/en/api/SIMD-API/basic_api/sync_control/inter_core_sync/CrossCoreWaitFlag_ISASI.md).

## Implemented first-version resolution

The mixed per-generation kernel uses bounded contiguous AIV copies, DMA-polled
generation flags and paired mode-2 AIC/AIV handoff. Publication and pull ACK
planes have shape-independent addresses inside the reserved 2 MiB IPC flag
region; a shape change cannot alias a preceding generation's ACK. Local
readiness is caller-owned and retained without resetting flags.

The [validation record](../TILELANG_ALLGATHER_GEMM_VALIDATION.md) records the
final two-rank runs, barrier-free shape reuse, one-launch evidence, separately
instrumented internal overlap and comparison with the frozen Host library.
The first version meets the functional/device-driven acceptance but does not
outperform the original pipeline for every tested shape.
